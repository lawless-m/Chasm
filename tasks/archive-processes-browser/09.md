Repo: /home/matt/Git/Whackford. Read ARCHITECTURE.md section 18 item 10 (`build --wasi` maps the four host words onto WASI preview1 with no scheduler) and `crates/core/src/program.rs` `compile` (where `live` is computed and `assemble` is called). M11 decision: a WASI build has no scheduler, so a program whose live words use any process or channel operation is refused with a new stable diagnostic code `E_WASI_UNSUPPORTED` (add it to `crates/core/src/diag.rs` `codes`; never rename existing codes), message "`build --wasi` cannot run processes: `<word>` spawns, or sends or receives on a channel; build without --wasi", `word` set to the first offending live word. Detect it from the compiled code rather than threading a flag: add `pub fn process_ops(c: &Compiled) -> bool` in `crates/core/src/check.rs` that is true when the code contains `I32Const(op)` immediately followed by `Call(FN_RING)` with `op >= layout::OP_SPAWN` (the `host.*` words emit opcodes 1 to 4 the same way; `ring.submit` in the prelude's channel words, `spawn` and `alt` all emit a literal opcode directly before `call rt.ring`). In `compile`, when `opts.wasi` and `live` (or every word when there are no roots) contains a word with a body for which `process_ops` is true, push the diagnostic and produce no module.

Tests in `crates/core/tests/compile.rs` (see `wasi_build_imports_preview1_and_exports_start` for how a WASI compile is made): a program with `: main ( -- ) [ ] spawn ;` under `wasi: true` fails with `E_WASI_UNSUPPORTED`; the same program under `wasi: false` compiles; a program whose only use of channels is in a dead word builds under WASI. Verify: `cargo test -p wack-core` and `cargo test -p wack-runtime --test wasi` (the runtime crate's package is `wack-runtime`). Done when both pass. Do not touch docs yet (the code goes into the reference table in the docs task).
