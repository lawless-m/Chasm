Read `crates/runtime/src/namespace.rs` (`Handle::Http`: the request is sent at the first read; `written`, `url`, `response`), `crates/runtime/src/net.rs`, `crates/runtime/src/native.rs` (the async `ring_enter` of the process-aware runner) and `crates/runtime/tests/net.rs` plus `crates/runtime/tests/common/http_server.rs` (a local test server). M11 decision for native I/O concurrency: in the process-aware runner only, the first READ on a `/net/http` or `/net/https` handle (the request itself) runs on a helper thread: the handle's `url` and `written` bytes are moved to `std::thread::spawn`, the process is marked `io_start` and parks; the scheduler runs others meanwhile; when the thread finishes, its `Result<Vec<u8>, i32>` is stored back into the handle as its `response` and the process is resumed (`io_done`) to complete the read from the response as today. Every other I/O operation (console, files, 9p, later reads of the same response) completes inline, and `/dev/cons` reads at `wack repl` are never offloaded (the REPL shares stdin with `read-line`). The driver loop must wait for thread completions when nothing is ready but some process waits on I/O (a channel of completions polled by the driver, no busy loop). Add `NativeHost` methods the runner needs to take the request parts out of a handle and put the response back, keeping `Host::read` unchanged for the synchronous path. Test in `crates/runtime/tests/procs.rs`: against the local server from `common/http_server.rs` extended with a `/slow` route that sleeps 300 ms before replying `slow\n`, a program that spawns two processes each doing `"/net/http/127.0.0.1:PORT/slow" read-file` and the main process receiving both results on a channel finishes in under 500 ms wall time and prints both bodies. Verify: `cargo test -p wack-runtime` and `cargo test -p wack-cli --test net`. Done when both pass. Do not change the browser host (fetch already parks there).
