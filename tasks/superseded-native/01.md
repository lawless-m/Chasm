Milestone M11 (CSP processes and channels, FUTURE.md section 9) needs green threads: several wasm activations in ONE wasmtime Store, each suspended inside a host import (`wack.ring_enter`) and resumed in ANY order (not last-in-first-out), with WasmGC references alive in their frames across the suspension (the engine uses the copying collector). The user has decided the native mechanism is wasmtime's `async` cargo feature (fibers); Asyncify, the Wasm stack-switching proposal, OS threads with separate stores, and components are ruled out. This task proves or refutes that mechanism and MUST NOT invent another design.

Setup: `cargo build -p wack-cli`. Write `tmp/spike.wack`:
```
struct point  x: i32
: churn ( -- )  200000 [ drop 7 point.new drop ] times ;
: park ( str -- )  0 host.open drop ;
export : a ( -- )  1 point.new :> p  "/park/a1" park churn  "/park/a2" park churn  "a:" print p point.x i32.to-str println ;
export : b ( -- )  2 point.new :> q  "/park/b1" park churn  "/park/b2" park churn  "b:" print q point.x i32.to-str println ;
: main ( -- )  a b ;
```
Build it: `./target/debug/wack build --no-opt -o tmp/spike.wasm tmp/spike.wack`. The module imports one function `wack.ring_enter` and exports `memory`, `a`, `b`, `main`; each `host.open` writes one submission entry into the ring in linear memory then calls `ring_enter` (ring layout: `crates/core/src/layout.rs`, serviced by `service_ring` in `crates/runtime/src/lib.rs`; `crates/runtime/src/native.rs` shows the sync host).

Harness: a throwaway cargo project `tmp/spike-native/` (add an empty `[workspace]` table to its Cargo.toml so the root workspace ignores it; path deps `wack-core = { path = "../../crates/core" }` and `wack-runtime = { path = "../../crates/runtime" }`; `wasmtime = { version = "49", default-features = false, features = ["cranelift","runtime","std","gc","gc-copying","async"] }`). Engine config as `wack_runtime::native::engine()` plus `async_support(true)`. Define `wack.ring_enter` with `Linker::func_wrap_async`: it reads the one pending submission (SQ_HEAD entry); for an OPEN of a path under `/park/` it parks: records a per-path slot and awaits a hand-rolled future (shared `Arc<Mutex<Option<i32>>>` + stored `Waker`) until the driver fills it, then writes the completion (CQ_TAIL) and advances SQ_HEAD; every other entry is serviced inline through `wack_runtime::service_ring` with a `NativeHost` whose console is `Console::Capture` (so `print` output is collected). Drive the `call_async` futures by hand with `std::task::Waker::noop()` in a poll loop.

Experiments, in order, recording each in `tmp/spike-native.md`: (1) Independent activations: start `a` with `Func::call_async`, poll until it parks at `/park/a1`, then try to start `b` while `a`'s future is still alive. Expect the borrow checker to refuse a second `call_async` on the same Store; record the exact error. (2) Nested activations: inside the host future for `/park/a1`, call `b` with `Func::call_async(&mut caller, ..)` (nested) so `b` parks at `/park/b1` inside `a`'s host call; then resume in the order a1, b1, a2, b2 and observe whether `a` can continue past a1 while `b` is still parked (non-LIFO), or whether `a` only continues after `b` finishes (LIFO). (3) Whichever variant lets both parked activations be resumed in the order b1, a1, b2, a2, check the console output contains `a:1` and `b:2` (the struct fields survived two GC churns across suspensions) and record the wall time of 10000 park/resume round trips. Also grep the wasmtime 49 source for any public API that runs several core-wasm activations on one Store as independent fibers (`~/.cargo/registry/src/*/wasmtime-49.0.1/src/runtime/fiber.rs`, `src/runtime/component/concurrent.rs`): note that `run_concurrent`/`call_concurrent` are component-model only and that a component cannot import the REPL's shared memory and tables, so they do not apply.
