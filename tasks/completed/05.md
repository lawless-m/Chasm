Context: jpeg/markers.wack has `struct scan (ncomp comps td ta ss se ah al data-at)` with `comps` an `array i32` of frame component indexes; markers.sos already refuses, as BAD_SCAN_HEADER, what libjpeg ERREXITs for one progressive scan (Se > 63, Ss > Se, Ss = 0 with Se != 0, Ss > 0 with more than one component, Al > 13, Ah != 0 with Ah != Al + 1) and MISSING_TABLE. What is left is the ordering of scans against each other: libjpeg keeps coef_bits[component][coefficient] (zigzag index 0..63), -1 until first scanned, then the Al of the latest scan; in start_pass_phuff_decoder, for each component of the scan: if Ss > 0 and coef_bits[ci][0] < 0, WARN (AC before DC); then for coefi = Ss..Se: expected = coef_bits[ci][coefi] < 0 ? 0 : coef_bits[ci][coefi]; if Ah != expected, WARN; coef_bits[ci][coefi] = Al. The M4 decision (strict mode only): each of those warnings (JWRN_BOGUS_PROGRESSION) is a refusal with code BAD_PROGRESSION (limits.wack; SECURITY.md "overlapping or out-of-order progressive scans"), checked before any entropy decoding of that scan. libjpeg's prev_coef_bits array exists only for output from a scan that ended early, which strict mode refuses, so it is not kept: say so in the header comment. For a sequential frame (SOF0/SOF1 with several scans) libjpeg does no such check and silently merges a component scanned twice; the M4 decision is to refuse BAD_PROGRESSION "component scanned twice" for a sequential component appearing in a second scan (libjpeg's own encoder refuses to write such a file: jcmaster.c validate_script), marking a scanned component's 64 coefficients as Al 0. A frame component never scanned is not an error (its coefficients stay zero, as in libjpeg).
