TASK: in jpeg/huffman.wack add, contract first, `huffman.decode ( bitreader hufftable -- i32 )`: one Huffman symbol, exactly as libjpeg's HUFF_DECODE. (1) If nbits < 8: bits.fill. (2) If nbits >= 8: look = the next 8 bits (bits.peek 8; no flag can be set since 8 bits are there); e = lookup[look]; nb = e >> 8; if nb <= 8: bits.skip nb and the result is e & 255; otherwise fall to the slow path with l = 9. (3) If nbits < 8 after the fill (a marker or the end of the data is near: the remaining code may still be complete, so no flag is set here), the slow path with l = 1. Slow path (jpeg_huff_decode, Figure F.16; write it as a separate word `huffman.decode-slow ( bitreader hufftable i32 -- i32 )` taking l): code = bits.get l (this may set exhausted and hand out zeros, which is the documented behaviour); while code > maxcode[l] (signed compare; -1 means no codes of that length): code = (code << 1) | bits.get 1; l += 1. The sentinel maxcode[17] = 0xFFFFF ends the loop by l = 17 at the latest. If l > 16: `BAD_ENTROPY_DATA "invalid Huffman code" refusal trap` (strict mode; libjpeg warns and fakes a zero). Otherwise idx = code + valoffset[l]; if idx < 0 or idx >= nsymbols: `BAD_ENTROPY_DATA "Huffman code outside its table" refusal trap` (cannot happen for a canonical table, but a refusal is better than an array trap); result symbols[idx]. Comment: why the lookahead is only taken with 8 real bits (the last code of a scan may be shorter than 8 bits and must not raise the exhausted flag), and that made-up bits after the end are always flagged by the reader, never silent.
