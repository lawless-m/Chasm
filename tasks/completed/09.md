Context: huffman.decode ( bitreader hufftable -- i32 ) fills when fewer than 8 bits are held, then, when 8 or more are held, does `t hufftable.lookup  r 8 bits.peek  array.at :> e`, `e 8 i32.shr_u :> nb`, and `nb 8 i32.le_s [ r nb bits.skip  e 255 i32.and ] [ r t 9 huffman.decode-slow ] if`, else decode-slow from length 1. bits.peek ( bitreader i32 -- i32 ) is `r n bits.ensure` then `r bitreader.buf  r bitreader.nbits n i32.sub  i32.shr_u  1 n i32.shl 1 i32.sub  i32.and`; bits.skip is `r n bits.ensure` then `r  r bitreader.nbits n i32.sub  bitreader.nbits!`; bits.ensure fills when nbits < n and, if still short, sets exhausted and pads with zeros. In the 8-bit branch of huffman.decode nbits >= 8 >= nb is already known, so both ensure calls are redundant: they cannot fill, cannot set exhausted, and only re-read nbits. bits.get ( bitreader i32 -- i32 ) is `r n bits.peek` then `r  r bitreader.nbits n i32.sub  bitreader.nbits!`, so a get runs ensure once in peek and reads nbits again afterwards; receive-extend and the progressive words call bits.get for every extra-bits field. This is about one symbol's worth of field traffic per Huffman symbol (big12 decodes a few million symbols, big12p's refinement scans and big12b12 more). The semantics are pinned by the huffman.decode tests (symbol and nbits after decoding, exhausted and marker after the last code of fx.tiny) and the bits.get tests.
