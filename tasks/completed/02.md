MECHANISM, chosen from evidence: wrap the decoder command in util-linux `prlimit` (/usr/bin/prlimit, present on this machine): `[prlimit, '--cpu=<S>:<S+1>', '--data=<BYTES>', wack, 'run', *FILES]`. Why: (a) RLIMIT_AS is unusable because wasmtime 49 reserves about 8.4 GB of address space per `wack run` (VmSize), but RLIMIT_DATA counts only committed private writable memory, which is exactly the wasm linear memory as it grows (the bump allocator `mem.alloc` in the prelude; `bytes` live there), wasmtime's GC heap (structs and `array` values) and the host's own allocations: measured, `prlimit --data=200000000` on an 80-megapixel arithmetic decode that needs 472 MB ends with `trap in \`mem.alloc\`: out of memory`, exit 1, and `--data=600000000` lets it decode; at 8 MB the Rust allocator aborts with `memory allocation of 2097152 bytes failed` (exit 134); a GC-heap failure reads `GC heap out of memory: no capacity for allocation of N bytes`. (b) A cgroup cap (`systemd-run --user --scope -p MemoryMax=`) also works but costs about 20 ms per run and kills with SIGKILL and no message. (c) A crates/ `--max-memory` option would duplicate what RLIMIT_DATA already bounds. (d) Python's preexec_fn is unsafe in a threaded program (the harness uses a ThreadPoolExecutor), so the wrapper, not setrlimit in a preexec_fn. (e) RLIMIT_CPU (`prlimit --cpu=S:S+1`) kills the decoder with SIGXCPU at S seconds of CPU: the shell sees exit 152, Python sees returncode -24 (signal.SIGXCPU). VALUES: `--cpu` default 30 (seconds), `--memory` default 1128000000 (MEM_BUDGET 1000000000 plus 128 MB headroom for the host: wasmtime engine and cached module about 7-14 MB of VmData, the 1 MiB PPM buffer, the GC heap and the input loader's doubling buffers), 0 disables either. Why 30 s: the slowest decode of any corpus file is 0.6 s of CPU (synthetic-m5/tw-pillow-xmp_test-pr4B.jpg, 2.1 megapixels), but a mutation that edits only the SOF dimensions to 16384 x 4882 (79986688 pixels, just under MAX_PIXELS) on an ARITHMETIC file produces a legal decode that djpeg also performs (both feed zeros past the end of data) of 80 megapixels from a 10 KB file: measured 4.4 s (8-bit 4:2:0 3 components), 6.4 s (8-bit 4:4:4), 9.6 s (8-bit 4-component 4:4:4), 10.0 s (12-bit 4:4:4), 11.0 s (12-bit 4-component 4:2:0); the worst legal case within the limits, 12-bit 4-component 4:4:4 arithmetic at 80 megapixels, extrapolates to about 18 s on this machine (beast, 40 cores), so 30 s is about 1.6x the worst legal decode and anything over it cannot be explained by header geometry within the limits: it is unbounded or amplified work. Huffman-coded files with the same edit refuse TRUNCATED or BAD_ENTROPY_DATA in well under a second.
