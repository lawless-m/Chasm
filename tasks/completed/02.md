In /home/matt/Git/Whackford/jpeg-decoder/ write jpeg/refuse.wack (depends on jpeg/limits.wack; files are named on the command line in order, there is no include). Whackford has no exceptions: a refusal is `"REFUSED CODE: message" trap`. A word that calls a trapping word still owes its declared outputs, so the pattern at every refusal site in the decoder is `CODE "message" refusal trap`, where the primitive `trap` ends an `if` branch or a `when` body (such a branch is exempt from matching the other branch). Under `wack run` a trap prints `trap in `word`: REFUSED CODE: message` on stderr and exits 1; the harness classifies by that text.

Contract first: write the `declare` and `test` lines, run `../target/debug/wack test jpeg/limits.wack jpeg/refuse.wack` to see them pending, then the bodies.

- `refusal ( str str -- str )`: code, message -> the string `REFUSED <code>: <message>`. Test: `test refusal : TRUNCATED "x" refusal -> "REFUSED TRUNCATED: x"`.
- `refusal-n ( str str i32 -- str )`: code, message, number -> `REFUSED <code>: <message> <number>` (for offsets and values in messages). Test with a literal number.
- A demonstration word showing the pattern, used by nothing else, e.g. `: refuse-demo ( i32 -- i32 ) dup 0 i32.lt_s [ LIMIT_DIM "negative" refusal trap ] when ;` with `test refuse-demo : -1 refuse-demo -> trap` and `test refuse-demo : 3 refuse-demo -> 3`.
- Header comment stating the pattern and that any trap whose message lacks `REFUSED ` is a decoder bug.
